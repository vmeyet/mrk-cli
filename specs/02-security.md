# 02 · Security

The input is untrusted: a README from a cloned repo, a paste, piped output.
The terminal is an interpreter: escape sequences can retitle windows, write the clipboard (OSC 52), change colours, or on some terminals worse.
mrk's job is to make rendering a hostile file equivalent to rendering a boring one.

## Rules

1. **One gate to the terminal.** Every span text and every link passes `sanitize` before being written: C0 controls (except tab, expanded to spaces, and newline, which never reaches a span), DEL, C1 controls (U+0080–U+009F), bidi overrides/isolates (U+202A–U+202E, U+2066–U+2069), bidi marks (U+200E, U+200F, U+061C), the zero-width space (U+200B), the word joiner and invisible operators (U+2060–U+2064), the deprecated format characters (U+206A–U+206F), the Mongolian vowel separator (U+180E), the interlinear annotation marks (U+FFF9–U+FFFB), the musical format characters (U+1D173–U+1D17A), the byte order mark (U+FEFF) and tag characters (U+E0000–U+E007F) are removed: they reorder or disguise text, as in a name that reads as another; an emoji subdivision flag, built from tag characters, shows as its black flag, and every width is measured on what is printed. The line and paragraph separators (U+2028, U+2029), which would break a line the layout never counted, become a space. The joiners U+200C and U+200D stay, since emoji sequences and Persian or Indic text need them. Tests feed ESC, BEL, OSC 52 and CSI sequences through every block kind.
   Picture sequences (kitty, Sixel) carry only bytes mrk derives from its own raster, never input text; the PNG decoder only reads the PNGs mrk drew.
   A jumbo title's concealed text is span text and passes `sanitize` like any; the double-height and conceal sequences around it are mrk's own.
   Inside tmux, only those picture sequences and the kitty query are wrapped for passthrough; span text never is, and `sanitize` strips the ESC that could open a passthrough of its own.
   Stderr is a terminal too: error reports, warnings, panic reports and clap's usage errors pass `sanitize` before being written, since they quote file names, arguments, environment values, input text and git's output.
   `--help` shows no environment value: mrk reads `MRK_THEME`, `MRK_WIDTH` and `MRK_ALIGN` itself, outside clap.
   `sanitize` is part of the library core, not the `cli` feature: a Document holds the input's text as written, so `Line::printable`, `document::printable` and `sanitize::link` are what a library user prints, and `docs/library.md` shows only them.
2. **Links are data.** An OSC 8 target is sanitized, capped at 2,048 bytes, and dropped (text kept) when it contains a character outside printable ASCII after percent-encoding or when its scheme is not `http`, `https`, `mailto` or `file`.
   A `file` link must name no host or `localhost` (`file:///…`, `file://localhost/…`), its path, percent-decoded once, holding no `\` and no empty, `.` or `..` segment (a trailing slash aside), which openers resolve into `//host/…`. A link to another host opens an SMB share on some systems, which sends it the user's credentials.
3. **No network, no surprise reads.** mrk reads the file named on the command line, stdin, its config file, and font files. Markdown images are never fetched or opened; they render as their alt text.
   Fonts are only read, never written: the first diagram or title picture lists `/System/Library/Fonts`, `/Library/Fonts`, `/usr/share/fonts`, `/usr/local/share/fonts`, `~/Library/Fonts`, `~/.local/share/fonts` and `~/.fonts`, four levels deep, following links to files but never to directories, and maps the `.ttf`, `.otf`, `.ttc` and `.otc` files of the label families and script fallbacks, or every one of them when a label needs a glyph those miss. No fontconfig file is read.
   Network exception: `mrk update`, and only when the user runs it, asks `git ls-remote --tags` for the latest release tag of the repo and its commit, then runs `brew update` and `brew upgrade` (`brew reinstall` with `--force`) when brew installed the running binary, else `cargo install --git … --rev <commit>` for that commit, checking that the binary installed reports that release and commit and that it is the `mrk` the `PATH` finds; rendering never reaches the network.
   Known exception, which its API gives no way to turn off: to measure the labels of pie, gantt and ER diagrams, and any label beyond ASCII, `mermaid-rs-renderer` loads the system fonts through fontdb (on Linux also the fontconfig files `/etc/fonts/fonts.conf`, `/etc/fonts/local.conf`, `$XDG_CONFIG_HOME/fontconfig/fonts.conf` or `$FONTCONFIG_FILE`, and the directories they list), then reads, or writes once, a copy of the face it picked under `$XDG_CACHE_HOME/mmdr/font-cache/` (`~/.cache` without it).
   The bytes it writes come from an installed font, never from the input; the bytes it reads back are whatever that file holds, so another program of the user can make ttf-parser parse a file of its choosing (`deny.toml`).
4. **Bounded work.** Input capped at 8 MiB; a diagram or a title picture is shrunk so its PNG stays within 4096×4096 pixels; SVG rasterisation refuses external `href`s (images, fonts) so a diagram label cannot pull a file off disk; a title enters its SVG as escaped character data, control characters dropped, so it can add no element.
   A Mermaid block over 64 KiB, or that reuses a subgraph id (read as mermaid-text reads it: every carriage return deleted, a bare `subgraph` named `__sg__`) or nests subgraphs over 16 deep (mermaid-text's recursion would overflow the stack, which no `catch_unwind` survives), reaches neither engine and shows as source with its note.
   Layout time grows far faster than the source: 500 edges between random nodes, 7.8 KB, took 10.8 s as a picture and 41.5 s as text, and 63 KB of them over 120 s.
   So `mermaid/budget.rs` counts what each layout grows with before that engine runs, on mermaid-rs-renderer's parse whenever it reads the diagram, for both engines, so `a & b --> c & d` counts its four edges; a diagram over its count goes to the other engine, then to source with a muted note naming the limit:

   | Engine | Diagrams | Counted | Limit |
   |---|---|---|---|
   | picture | flowchart, class, state, ER, requirement, architecture | links: nodes, edges, edge labels, subgraphs, state notes, and each edge between two nodes already joined once per earlier one | 150 |
   | picture | sequence | participants, messages, notes, and each part of a frame (an `alt` with one `else` is two) | 400 |
   | picture | every other kind | nodes, edges, subgraphs, git commits, C4 shapes and relations, pie slices, timeline periods and events, xy chart categories, series and values | 600 |
   | text | class | relations | 32 |
   | text | sequence, git | lanes, as mermaid-text reads them: a sequence's participants, a git graph's branches; every row is drawn across all of them | 200 |
   | text | pie, gantt, timeline, journey, mind map, kanban | nothing: drawn row after row, 64 KiB of any took under 30 ms | none |
   | text | every other kind | edges, and nodes on no edge, plus subgraphs | 100 |

   When mermaid-rs-renderer cannot parse a diagram mermaid-text reads, the text counts come from a scan of the source: each arrow counts the nodes on its left times those on its right (`a & b & c --> d & e` is six).
   A document's diagrams share a budget of 12 s of layout, each diagram charged what the engine that will draw it counts, at the slowest rate measured for that count: a layered layout slows down per unit as it grows (links²/7 ms for a picture, edges²/8 ms as text, relations² × 7/4 ms for a class diagram as text), a sequence or the other kinds drawn in rows 1 ms per element, a sequence or git graph as text 1 ms per lane; a picture adds 20 ms to fit and draw it, every diagram costs at least 5 ms, one refused by its own count costs nothing, and a repeated source is charged once.
   Each diagram, in reading order, is laid out when its charge fits what is left of the budget, else it shows as source (`over the 12 s of layout a document's diagrams share`), so a document lays out at most 2,400 diagrams and the cache keeps them all.
   Each distinct source is parsed once per render, and the graph that counted it is the one laid out; once less than 5 ms is left, no further diagram is parsed and every one after shows as source with that note.
   Parsing runs outside the deadline: 8 MiB of distinct flowcharts over their count took 0.9 s, where parsing each up to three times took 2.5 s.
   Without a deadline the counts alone decide what is drawn: the library lays every diagram out on the calling thread with no clock, and a picture comes out the same on any machine and in any process; mermaid-text's text does not, since it orders the boxes of a subgraph differently from one process to the next.
   The binary gives each render of a document 10 s for its diagrams: each engine runs on a thread of its own with a 64 MiB stack, a diagram still laying out at that moment is given up on and shows as source (`too slow to lay out`), cached so a pager resize starts neither engine on it again, and the diagrams not started yet show as source (`out of time for the document's diagrams`), laid out by a later render, which gets 10 s of its own.
   A thread given up on cannot be stopped: it runs to its end and its result is dropped, which costs CPU only in the pager, since a one-shot `mrk` exits without waiting for it; the fonts a picture needs load on the calling thread, never on one given up on.
   Measured on an Apple M5 in a release build, through `markdown::render` with no deadline, on the bench corpus of twelve real diagrams (CI pipeline, auth flow, two state machines, ER, class, sequence, microservices, data pipeline, Kubernetes, module dependencies, incident flow): as one document all twelve draw, eleven as pictures and the class diagram as text since mermaid-rs-renderer cannot parse it, in 3.6 s, 0.03 to 1.25 s each (the module graph, 130 links), and lay out again on a resize in 0.3 s.
   The slowest diagram within the counts took 3.1 s as a picture (95 edges between 45 random nodes, 145 links; 120 fanned-out edges, 2.9 s) and 1.2 s as text (100 edges).
   mermaid-text draws each row of a sequence across every participant, and of a git graph across every branch: a 64 KiB sequence of 7,900 participants took 3.4 s as text, charged 5 ms, and 8 MiB of them were still drawing after 180 s.
   A lane is at least 6 columns wide (11 for a participant), so more than 200 never fit the widest text, 1,000 columns: the limit refuses nothing mrk could draw.
   At the limit, 64 KiB of messages or notes across 200 participants took at most 0.13 s and of commits across 200 branches 0.03 s; 128 distinct such sequences in one document took 6.3 s, within the budget.
   Counting lanes takes mermaid-text's parse on top of mermaid-rs-renderer's, and both grow with the square of the participants: a 64 KiB block of 7,900 participants takes 0.09 s to count, so 8 MiB of them took 9.9 s, outside the deadline.
   The chart marks and frame parts a picture counts lay out far faster than they are charged: at their limits, 397 nested frames took 0.07 s, 599 xy chart values 0.06 s, 600 pie slices 0.04 s, and 40 distinct such diagrams in one document at most 1.8 s; uncounted, 142 pies of 5,000 slices (8 MiB) were still laying out as pictures after 30 s, where now they draw as text in 2.4 s.
   The slowest documents within the budget took 8.7 s as pictures (30 fanned-out graphs, four drawn) and 3.7 s as text (34 graphs of 95 random edges): the budget is charged at worst rates the realistic diagrams stay well below, so the binary's 10 s is what bounds an adversarial document on a slower machine.
   A panic inside a renderer is caught and its diagram shows as source; the binary's panic hook drops the report, which quotes the diagram, and sanitizes every other one (rule 1), and the pager leaves it out of the report it prints on exit.
   syntect's time on a line can grow with the square of its length: a JavaScript regex literal on one line took 1.2 s at 8 KB and 15 s at 32 KB, and 8 MB of `a=1;` on one line 21 s and 2.4 GB.
   So a code block is highlighted only up to its first line over 512 bytes, and a document highlights at most 256 KiB of code, each block, in reading order, that fits what is left; the rest is plain text, the label kept (`code/budget.rs`).
   The slowest document within these limits took 1.8 s (512-byte regex literals filling the 256 KiB), the 8 MB line 0.09 s, and a 5,000-line Rust file (200 KB) 0.13 s (release build, Apple M5).
   `diff::sections` compares words with a Myers diff, whose time grows with the product of the two sides when they differ throughout: 40,000 words all changed took 1.4 s and 100,000 took 9.6 s, while 100,000 words with one in a hundred changed took 7 ms (release build, Apple M5).
   So the diff is bounded by counts alone, which keeps its answer the same on every machine: a pair of sections over 20,000 words, both sides counted (0.4 s at worst), is marked whole without a diff, and so is a pair over what is left of the 50,000 words one call diffs (1.1 s at worst, pairs of 20,000 words all changed); past 10,000 sections, both sides counted (0.4 s at worst, all different), only the equal sections at both ends pair. Pairing a run of changed sections by kind searches each kind with no partner left once (200,000 headings against 200,000 paragraphs: 0.4 s).

5. **Terminal queries are parsed strictly.** Responses are read from `/dev/tty` with a timeout, bounded in length; bytes between replies (keys typed meanwhile) are skipped, and a malformed reply means "unsupported".
6. **Config is data.** Strict TOML, unknown keys rejected, no paths or commands in it.
   `MRK_PAGER`, set by the user, is split into words (`shell-words`) and run without a shell, so nothing in it expands; the pager's search query goes through `sanitize` like span text.
7. **No `unsafe`**, enforced by `unsafe_code = "forbid"`; `cargo deny check` clean.
